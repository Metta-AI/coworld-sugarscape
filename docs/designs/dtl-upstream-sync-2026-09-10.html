DTL upstream sync

A daily GitHub Actions workflow finds new upstream DTL Sugarscape commits. Codex bumps the submodule and adapts the v3 coworld wrapper. The workflow opens a PR for review, and it alerts James when a change needs a design decision and not a mechanical repair.

Executive Summary

The v3 coworld wraps the unmodified upstream DTL Sugarscape engine as a git submodule1, and upstream2 moves without us. On 2026-09-10 upstream is three commits ahead of our pin, and nobody knows until a person bumps the pin by hand. This document proposes two thin GitHub Actions workflows and one unit-tested script. Each day a detect step gets the upstream commits and bumps the submodule. Then a Codex step adapts the wrapper, the tests, and the docs, and writes a structured report. Then a publish step turns that report into a commit, a PR, labels, and alerts.

The most important decision is the classification of each upstream change into one of three classes: no-impact, mechanical, or needs-design. The script, not the agent, forces needs-design when the trajectory hash changes or a test fails. This rule prevents a quiet update of the hash constant when the engine semantics change. The cost is a GitHub App token, three broker-sourced secrets, and branch protection on main, which does not exist today. A human merges each PR.

1 · Problem

  • The wrapper depends on an upstream engine that changes without us. On 2026-09-10, upstream is three commits ahead of our pin.
  • Each upstream change goes into one of three classes, and only one class is fully mechanical.
  • Today the only detection method is a person who bumps the pin by hand.

Since the submodule change1, the v3 coworld imports the upstream DTL Sugarscape engine exactly as published, with no local patches. That is the correct shape for a wrapper, but the engine authors set the speed of change. Each upstream commit can have one of three effects on us. It is possible that nothing we import changed, for example GUI or plot work. It is possible that something we import changed, and the wrapper and its documentation can absorb the change mechanically. Or the engine got a new feature, and a design decision is necessary on how SugarLang, seats, targets, or scoring show it to players.

Now, no part of the system finds these cases automatically. The pin drifts until a person bumps it, and then the three cases arrive together in one manual diff. The three commits that wait on 2026-09-103 are a small example. They touch the GUI, the simulation shutdown, and the plots. A person must read all three to know that none of them has an effect on the wrapper.

2 · Goals and Non-goals

  • Find upstream changes each day and on demand. Let a coding agent make a PR for review, with a written rationale.
  • Alert James, with the reasoning of the agent attached, when a change needs design work.
  • Do not auto-merge. Do not regenerate the target catalog. Track only upstream master. Do not depend on a persistent machine.

Goals

The system must find upstream changes on a daily schedule and when a person starts it by hand. When it finds one, a coding agent must bump the submodule, adapt the wrapper and the docs, and operate the test suite. The agent must then make a PR that a reviewer can evaluate from its body alone, because the body has a written rationale. When the agent decides that a change needs design work, not mechanical adaptation, the system must alert James with that reasoning attached.

The full process must leave an audit trail. The classification and reasoning of each run are in the PR body. Each credential that the workflow uses is a repository secret that came from the token broker.

Non-goals

The system will not auto-merge, and a human merges each sync PR. The system will not regenerate the target catalog. When the engine semantics change, it is possible that the catalog is stale. The decision on that is the design work that this system escalates. The system will not track upstream branches other than master, and it will not track upstream tags, of which there are none2. The system will not operate on a persistent machine, and all steps operate on GitHub-hosted runners.

3 · Architecture

  • Two workflows and one script. The workflows are thin. The script holds each decision, thus you can unit-test it and operate it from a laptop.
  • ci.yml is new. The repository has no CI today.
  • The sync workflow has five steps: checkout, detect, Codex, publish, and the CI run that the push starts.

The design adds the files that follow. The prompt and the report schema are in version control with the repository, and we review them as code.

.github/workflows/ci.yml          pytest on every PR and push to main (new; the repo has no CI today)
.github/workflows/dtl-sync.yml    schedule (daily) + workflow_dispatch
tools/dtl_sync.py                 detect | publish subcommands
tools/dtl_sync/PROMPT.md          the Codex task prompt, versioned with the repo
tools/dtl_sync/REPORT_SCHEMA.json the structured report Codex must write
tests/test_dtl_sync.py            unit tests for the script against a throwaway git repo

Step order in the sync workflow

The workflow does five steps in sequence. First, actions/checkout gets the repository with submodules: true and uses the app token from §8, thus later pushes start ci.yml. Second, tools/dtl_sync.py detect operates (§4). It gives changed=true|false, branch, and pr_number when an open sync PR exists. It writes a work directory at build/dtl-sync/ that has upstream.log, upstream.diff, and pytest-before.txt. It stops early when nothing changed, unless a person started the run with force=true.

Third, openai/codex-action4 operates with prompt-file: tools/dtl_sync/PROMPT.md, sandbox: workspace-write, effort: high, the default model, and output-file: build/dtl-sync/report.json. The prompt refers to the work directory files by path. Fourth, tools/dtl_sync.py publish (§7) validates report.json against the schema. It commits the changes of Codex with a message from the report, pushes the branch, makes or updates the PR, applies labels, and sends alerts. Fifth, ci.yml operates on the pushed branch, because the push used the app token and not the default workflow token.

Manual dispatch inputs

A manual dispatch accepts two inputs. upstream_ref has the default value master and also accepts a commit. Thus you can target a specified upstream state or do a past run again. force has the default value false. When force is true, the run continues when the gitlink already matches upstream.

4 · The Detect Step

  • Get the upstream commits, compare with the pin on main, and stop if they match (unless forced).
  • One cumulative PR. If an open dtl-sync PR exists, bump on its branch, thus the PR always tracks the upstream head.
  • Write the log, the diff, and a pytest run before the change as input for the agent. Test failures here are input, not a workflow failure.

Detect first gets upstream_ref from the upstream repository2 into the submodule. Then it reads the current pin from the gitlink on main with git ls-files --stage1. If the pin is equal to the new commit and force is false, the run does nothing.

If not, detect looks for an open PR with the label dtl-sync. If one exists, detect checks out the branch of that PR and bumps on it, thus the PR always tracks the upstream head. This was the choice of James: one cumulative PR, not a queue of small PRs. If no such PR is open, detect makes a branch with the name dtl-sync/<YYYY-MM-DD>-<short-sha> from main. Then detect checks out the target commit in the submodule and stages the gitlink.

Next, detect writes the inputs for the agent. upstream.log is git log --stat from the main pin to the target, thus a cumulative PR always shows the full range and not only the last increment. upstream.diff is the full diff without plots/, data/, examples/, and README. This keeps the context of the agent on code that can have an effect. The log lists those files, thus nothing is hidden.

Last, detect operates .venv/bin/python -m pytest -q -p no:cacheprovider and saves the output as pytest-before.txt. Failures at this point are the expected input for Codex, not a workflow failure. A red suite is the signal that the wrapper needs adaptation.

5 · The Codex Task

  • The prompt is the load-bearing artifact, and we review it as code.
  • The agent never edits the submodule. It makes the smallest change to the wrapper and the docs, and it operates the suite again.
  • The agent never repairs a changed trajectory hash with an update of the constant. It escalates the change.
  • The output is a structured report.json that the script validates.

The contract of the prompt has five parts. First, the agent reads the agent guide of the repository5, the wrapper module6, upstream.log, upstream.diff, and pytest-before.txt. The agent must never edit a file in the submodule. The workflow also enforces this rule: it rejects the run if the submodule tree is dirty after Codex stops.

Second, the agent makes the smallest change to src/coworld/, tools/, tests/, and the docs that keeps the wrapper correct against the new upstream. Third, it updates the documentation in the same pass and obeys the documentation rules of the repository5. Fourth, it operates the suite again. If EXPECTED_TRAJECTORY_HASH7 no longer matches, the agent must not update the constant. A changed hash shows that the engine semantics changed, and the classification in §6 must escalate that. The agent records the old hash and the new hash in the report.

Fifth, the agent writes report.json, which must match REPORT_SCHEMA.json. The report has the field classification. The field summary has two or three sentences that become the PR title and the alert text. The field upstream_range gives the commit range. The field files_changed lists the edited files.

The field tests has passed, failed, and trajectory_hash_changed. The field design_questions is a list, and it is mandatory when the classification is needs-design. The field reasoning has the full argument for the classification, written for James.

6 · Classification

  • Exactly one of needs-design, mechanical, or no-impact.
  • The script forces needs-design on a changed trajectory hash or a failed test, whatever the choice of the agent.
  • The test for the agent: must a maintainer decide whether and how players see this, and not only that the code still operates?

The agent must select exactly one classification. The script enforces the first rule mechanically, thus an argument cannot bypass it.

needs-design: the script forces this class, whatever the agent reported, when trajectory_hash_changed is true or tests.failed is not zero. The agent must also select this class for some upstream additions or changes. These are a configuration key, an agent trait, a decision model, an ethics model, a statistic, or a mechanic. This applies when SugarLang, the seats layer, the targets, the scoring, or the replay format can show the change or must account for it. The prompt gives the agent this test: must a maintainer decide whether and how players see this, and not only that the code still operates?

mechanical: the wrapper, the tools, the tests, or the docs needed edits, the suite is green, and the trajectory hash is unchanged.

no-impact: upstream touched only files that the wrapper never imports (GUI, plots, README, examples, data scripts), the suite is green, and no wrapper edits were necessary.

Why the script overrides the agent The trajectory hash is the one signal that an argument cannot remove. If the hash moved, the simulation gives different results than before. Then a person must decide whether the targets and the catalog still have the same meaning. A mechanical override makes sure that a persuasive but wrong argument from the agent still reaches James with the needs-design label.

7 · The Publish Step

  • A missing or invalid report becomes needs-design with the raw Codex output attached, thus a confused run still reaches James.
  • Refuse to publish if the submodule tree is dirty.
  • Each run makes the PR body again from the report, and the body keeps a run log, thus a cumulative PR keeps its history.
  • Alerts go out only on needs-design, and only one time for each distinct upstream commit.

Publish first validates report.json. A missing or invalid report is not a silent failure. Publish treats it as needs-design with the raw Codex output attached, thus a confused agent run reaches James and does not disappear. Then publish refuses to continue if git status --porcelain in the submodule shows a change. This is the second line of defense behind the prompt instruction to never touch upstream code.

The commit subject is dtl-sync: <classification>: <summary first sentence>. The commit body comes from the report and includes the upstream range. The push uses the app token. If no PR exists, publish makes one. If a PR exists, publish updates its body.

Publish makes that body again from the report on each run. The body has the classification, the summary, the test results, the reasoning, and the design questions. It also has the upstream range with a link to the upstream compare view. It also has a run log with one line for each run. Thus a cumulative PR keeps its full history when publish writes the body again.

Each sync PR has the label dtl-sync, and publish adds needs-design when applicable. Publish removes the needs-design label only when a later run on the same PR reports a different classification and the trajectory hash matches main again.

Alerts go out only on needs-design, and only one time for each distinct upstream commit. The run log records the commits that caused an alert, thus a daily run against an unchanged upstream does not send the alert again. When an alert goes out, three things occur.

Publish assigns James on the PR. Publish sends a Discord DM through the agent bot with the summary, the design questions, and the PR link. The recipient snowflake is in the repository variable DTL_SYNC_DISCORD_USER_ID. Publish makes an Asana task in the project that the repository variable DTL_SYNC_ASANA_PROJECT_GID identifies (James must give the GID). The task title comes from the summary, and the task notes have the reasoning and the PR link.

8 · Credentials

  • The workflow gets three secrets one time through the metta token broker, which logs who asked and why. It stores them as repository secrets.
  • A fourth secret, the GitHub token, must not be the default GITHUB_TOKEN. If it is, the sync PR has no CI.
  • Each secret is available only to the steps that need it.
SecretBroker scopeUsed by
OPENAI_API_KEYopenai.inferenceopenai/codex-action, via its openai-api-key input4
DISCORD_BOT_TOKENdiscord.post (approval tier)publish alert step
ASANA_PATasana.rwpublish alert step
DTL_SYNC_GITHUB_TOKENNot a broker scope. A GitHub App installation token (preferred) or a fine-grained PAT with contents: write and pull-requests: write on this repository onlyactions/checkout, and the publish push and PR steps

The push cannot use the default GITHUB_TOKEN, because events that this token makes do not start other workflow runs8. A sync PR pushed with that token has no CI result, and that defeats the purpose of the review. Each secret is available only to the steps that need it. The Codex step receives the OpenAI key through the proxy of the action4 and nothing else: no git credential, no Discord token, no Asana token.

9 · Security

  • The repository is public. The sync workflow never operates on pull_request, thus fork PRs cannot reach the secrets.
  • The agent reads third-party code and commit messages, which is a prompt-injection surface. Five mitigations apply.
  • Branch protection on main is part of the rollout. It does not exist today.

Because the repository is public, the trigger list is important. dtl-sync.yml operates only on schedule and workflow_dispatch, never on pull_request. Thus a PR from a fork cannot start the workflow with access to the repository secrets.

Risk: prompt injection through upstream The agent reads upstream commit messages and diffs verbatim. A malicious or strange upstream commit can try to steer it. The mitigations are in layers:
  • The sandbox of the action4
  • No git credential in the Codex step, thus the agent cannot push
  • The hard refusal of the script to publish a dirty submodule tree
  • A human merge on each PR
  • Branch protection on main with one approved review and a green ci.yml.
The rollout (§11) sets up the branch protection, which does not exist today.

The app token of the workflow has a scope of this repository only. Thus a compromised publish step cannot reach other Metta-AI repositories.

10 · Testing and Acceptance

  • Unit tests operate detect and publish against a temporary git repository with a false upstream and a stubbed GitHub client.
  • actionlint operates on the two workflows in ci.yml.
  • Acceptance is a manual dispatch against the three upstream commits that wait on 2026-09-10.

The unit tests in tests/test_dtl_sync.py operate the script against a temporary git repository with a false upstream bare repository and a stubbed GitHub client. They cover these cases:

  • No operation when the pin is already at the head
  • A new branch when no sync PR is open
  • A bump on an open PR
  • The forced needs-design on a changed trajectory hash
  • The forced needs-design on failed tests
  • One alert for each upstream commit and no second alert
  • The refusal to publish a dirty submodule.

ci.yml checks the two workflow files with actionlint.

Acceptance is a manual dispatch against the three upstream commits that wait on 2026-09-103: a dark-mode GUI change, an exit() in the simulation shutdown, and bar-chart plots. The expected result is a classification of no-impact or mechanical, a green suite, an unchanged trajectory hash, and no alert. If the run escalates one of these three commits, the prompt or the classification rules need work before we make the schedule active.

11 · Rollout

  • Six steps, in sequence. The schedule becomes active last, behind a repository variable.
  • The workflow file can land before the secrets exist, because the schedule ships disabled.
  1. Merge the submodule PR1.
  2. Land ci.yml and set branch protection on main.
  3. Make the GitHub App (or PAT) and the four secrets. Set the two repository variables (the Discord user id and the Asana project GID).
  4. Land dtl-sync.yml, the script, the prompt, the schema, and the tests.
  5. Do the acceptance dispatch from §10 and review the PR that it opens.
  6. Make the schedule active. The committed workflow keeps the schedule disabled behind the repository variable DTL_SYNC_ENABLED=true, thus the workflow file can land before the secrets exist.

12 · Alternatives Considered

  • We rejected a persistent EC2 box. It is a machine to keep alive for a few minutes of work each day.
  • We rejected Dependabot submodule bumps. Workflows that Dependabot starts cannot see the OpenAI key.
  • We rejected a Metta-AI fork with a patch branch, together with the submodule change. There are no patches to carry.
Decision: hosted runners, not a persistent EC2 box with cron calling Codex

A long-lived box with cron was plausible because it is the simplest picture: a machine that wakes, operates Codex, and pushes. We rejected it because it adds a machine to keep alive, patched, and authenticated, for a job of a few minutes each day. The job needs nothing that a hosted runner lacks. If the agent needs a long-lived environment in the future, metta box new can make one at that time.

Decision: the workflow bumps the submodule itself, not Dependabot

The gitsubmodule ecosystem of Dependabot can open bump PRs on its own, and a workflow on that PR can then operate Codex. We rejected it because workflows that Dependabot starts get a read-only token and see only Dependabot secrets, not Actions secrets9. Thus the Codex step has no API key. The bump is one git command, and the workflow does it.

Decision: a pristine submodule, not a Metta-AI fork carrying a patch branch

A fork gives a place to hold local patches on top of upstream. We rejected it together with the submodule change1. The wrapper needs no upstream patches, thus a fork only adds a rebase step to each sync and gives nothing.
