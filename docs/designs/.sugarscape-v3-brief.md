## 1. Context and premise

Three generations:

- **v1** (`archived/v1/`, frozen): a byte-parity Nim port of the DTL Python Sugarscape with per-tick, per-agent movement control bolted on over WebSocket. Worked, certified, but the decision edge was synchronous and slow (worst case ~6.4 s/timestep with 64 seats timing out), and only movement could be delegated.
- **v2** (`archived/v2/`, design-complete, never implemented): a from-scratch deterministic Nim implementation with agent-level player control, phased timestep, negotiation. Its decision **D1** ("v2 is our own implementation of Sugarscape, not DTL", `docs/what-is-a-coworld.md` §Decisions) was justified by exactly one thing: DTL is a batch social-science simulator with no seam for external per-tick controllers, so per-tick control could only be bolted on.
- **v3** (this design): James's direction (2026-08-11). Players do **not** control agents per tick. Each player submits, once, a **ruleset** — a declarative specification of the movement rule their agents will follow — and the simulation then runs to completion with no further player interaction. This dissolves D1's rationale entirely: with no per-tick control edge, DTL's batch architecture stops being an obstacle and becomes the cheapest correct choice. **v3 is a direct clone of the DTL Python implementation** (`nkremerh/sugarscape`, Unlicense, pinned copy at `archived/v1/reference/dtl-python/`), extended with one custom Agent subclass that interprets rulesets, plus a thin coworld edge.

James's framing of the goal: across episodes, the winning player is the one with the **most explanatory ruleset (or ruleset generator)** — one that, applied to many different Sugarscape configurations and many different target distributions (drawn from the Sugarscape literature and from real-world observed distributions), reliably makes the simulation's emergent outcome match the target. This is Epstein's generative social science motto operationalized as a game: "If you didn't grow it, you didn't explain it." The player is cast as a computational social scientist; the score is explanatory power.

## 2. Game concept (one paragraph)

An episode assigns each player (seat) a **target outcome distribution** — e.g. "a wealth distribution with a Pareto tail and Gini ≈ 0.5" or "endemic disease at 20% prevalence" — plus the full game config. Each player answers with a single **ruleset**: a small declarative program (traits + a movement decision list) that all agents assigned to that seat will follow. The DTL simulation then runs N ticks (default 1000). At the end, the game measures the actual outcome distribution for each seat and scores it by distance to that seat's target — closer is better. Leaderboards rank players by an EWMA of episode scores, not Elo, so single-player episodes are first-class.

## 3. Episode flow and player protocol

Phases:

1. **Boot.** Game container reads config from `COGAME_CONFIG_URI`, seeds the RNG, builds the DTL world, serves `/healthz`.
2. **Submission window.** Each player connects to `WS /player?slot=n&token=t` (bad token rejected at handshake, per platform contract). The game immediately sends one observation. The player replies with one action (the ruleset) and may disconnect. Window closes when all seats have submitted valid rulesets or after `player_connect_timeout_seconds` (default 180).
3. **Run.** The simulation free-runs N ticks with zero player I/O. Spectator frames stream to `WS /global` as it runs.
4. **Score & write.** Measure distributions over the final window, compute scores, write results JSON to `COGAME_RESULTS_URI` and the replay artifact to `COGAME_SAVE_REPLAY_URI`, send a final `result` message to any still-connected clients, exit.

Messages are game-owned JSON over WS (platform fixes only routes and tokens — `docs/what-is-a-coworld.md` §1.2):

- Game → player `observation`: `{type:"observation", protocol:"sugarscape-v3/1", seat:n, config:{...full effective game config...}, target:{id, variable, scope, support:[lo,hi], bins:[...], probs:[...], window, source}, ruleset_schema:{version:1, limits:{max_nodes:256, max_depth:16, max_bytes:32768}}}`.
- Player → game `action`: `{type:"action", ruleset:{...}}`.
- Game → player `ack`: `{type:"ack", valid:true}` or `{type:"ack", valid:false, errors:[...]}` — an invalid ruleset can be corrected and resubmitted until the window closes.
- Game → all `result` at end: per-seat scores + summary.

**Fault semantics are trivial by construction** (contrast with v1's 100 ms fallback machinery and v2's frozen-agent rule A3): after the submission window there is nothing left for a player to fault on. A seat that never submits a valid ruleset gets the **null ruleset** — no trait overrides, no movement rules — which by definition (see §4 semantics) is exactly vanilla DTL behavior. The seat is still scored honestly against its target. Results record `submitted:false` for that seat.

## 4. The ruleset DSL

The heart of the design. Requirements: expressive enough that ruleset design is a real intellectual game; total and deterministic (no halting problem, no sandbox escape — it is data, not code); cheap to evaluate inside the per-tick movement loop; legible enough that a leaderboard-topping ruleset can be read and understood (that's the scientific payoff).

### Shape

```json
{
  "version": 1,
  "traits": { "aggression": 0.0, "trade": 1.0, "lending": 0.0, "fertility": 1.0 },
  "movement": [
    { "if":    ["<", ["get","agent.ttl"], 3],
      "score": ["get","cell.welfare"] },
    { "score": ["-", ["get","cell.welfare"],
                ["*", 0.4, ["get","cell.distance"]],
                ["*", 2.0, ["get","cell.pollution"]]] }
  ]
}
```

Two blocks, both optional (both absent = the null ruleset = vanilla DTL agent):

- **`traits`** — scalar behavioral dials applied to every agent of the seat at spawn, clamped into per-variant allowed ranges. v3.0 traits map directly onto per-agent factors DTL already implements: `aggression` → `aggressionFactor` (combat, `agent.py:717`), `trade` → `tradeFactor` (`agent.py:601-603` — 0 disables trading), `lending` → `lendingFactor` (`agent.py:432`), `fertility` → `fertilityFactor` (`agent.py:501`). This buys player control over combat/trade/lending/reproduction intensity **without touching those subsystems' code** — DTL already parameterizes them per agent. A variant locks a dial by declaring a degenerate range.
- **`movement`** — an ordered **decision list**. Each tick, when the agent moves, conditions (`if` expressions over agent/world state) are evaluated top-down; the first matching rule (a rule with no `if` always matches; the list must end with one) supplies the **score expression**, which is evaluated once per candidate cell; the agent moves to the argmax cell. Ties: smaller travel distance, then DTL's existing shuffled iteration order — identical tie policy to stock DTL (`agent.py:1430-1434`), preserving determinism.

### Expressions

JSON s-expressions: `["op", arg, arg, ...]`, numbers as literals, `["get", "name"]` for features. Operators: `+ - * / min max abs neg pow < <= > >= == != and or not if`. Totality rules: `/` by zero → 0; `pow` with base < 0 or |exponent| > 8 → clamped; all results finite floats (NaN/Inf → 0). Budgets (validated at submission): ≤ 256 nodes total per ruleset, depth ≤ 16, ≤ 32 KB JSON. Evaluation is O(nodes) per candidate cell; the interpreter compiles each expression once to nested Python closures at submission time, so per-eval cost is small.

### Feature vocabulary (v3.0)

| Namespace | Features | Source in DTL |
|---|---|---|
| `agent.*` | `sugar, spice, wealth, sugarMetabolism, spiceMetabolism, vision, movement, age, ttl, mrs` | direct attributes; `ttl` = `findTimeToLive()` (`agent.py:1114`), `mrs` = `findMarginalRateOfSubstitution()` (`agent.py:1024`) |
| `cell.*` | `sugar, spice, pollution, distance, occupied, preyWealth, welfare` | candidate record from `rankCellsInRange()` (`agent.py:1396-1444`); `welfare` = DTL's own Cobb–Douglas `findWelfare()` for this agent at this cell (`agent.py:1171-1202`), so the stock greedy rule is expressible as `["get","cell.welfare"]` |
| `world.*` | `timestep, population, gini, meanWealth` | per-tick `runtimeStats` DTL already computes (`sugarscape.py:82-95`) |

The `world.*` namespace is a deliberate differentiator: it lets rulesets be **macro-feedback controllers** ("if Gini is above target, favor poor-agent-friendly moves"), which is precisely the skill the game wants to reward — steering emergent distributions.

### Semantics guarantees

- The candidate cell set is **unchanged from DTL** — vision, occupancy, prey-validity and retaliation filtering all still apply (`agent.py:1413-1428`). The ruleset only replaces the *ranking* among valid candidates. Combat stays a movement consequence exactly as in DTL: moving onto a valid prey cell is an attack, so rules can seek or avoid combat via `cell.occupied`/`cell.preyWealth`.
- Everything downstream of movement — collection, metabolism, trade, reproduction, lending, disease, aging, death, inheritance (`agent.py:569-599` `doTimestep`) — runs stock DTL code, modulated only through the trait dials.
- Deterministic: one seeded `random.Random` stream (DTL uses the global `random` module, seeded once), pure interpreter, fixed tie policy. Same config + seed + rulesets ⇒ identical run on the same CPython version. The container pins the Python version, so hosted runs are reproducible; we do not promise cross-version bit-stability.

### Alternatives rejected for the DSL

- **Arbitrary code submission (Python snippet / WASM blob) —** maximum expressivity, but sandboxing, resource-abuse, and determinism burdens are all severe, and winning rulesets would be unreadable. The DSL is data; there is nothing to escape.
- **Flat weight vector over fixed features** (score = w·f) — trivially safe but no conditionality; the game collapses into linear regression and the expressivity ceiling is hit in a week.
- **Turing-complete rule language (loops/recursion, full GP)** — halting and perf problems inside a 1000-tick × ~1000-agent × ~24-candidate loop; audit burden; overkill for movement.
- The chosen decision-list + expression-tree design is the classic genetic-programming-on-Sugarscape formulation, so it is also friendly to players who want to *evolve* rulesets offline.

## 5. Seats, agents, and lifecycle

- Config declares `seats` (= number of player slots) and DTL's `startingAgents`. Validation requires `startingAgents % seats == 0`; initial agents are assigned round-robin, so allocation at t=0 is equal.
- **Replacements** (DTL `agentReplacements` rule R): a replacement agent inherits the seat of the agent it replaces.
- **Newborns** (DTL reproduction): the child is assigned to one of its two parents' seats by a 50/50 draw from the simulation's seeded RNG stream. (v2's fancier Thue–Morse alternation is noted as an option if 50/50 proves noisy; not v3.0.)
- **RulesetAgent instantiation** follows DTL's existing decision-model seam: `sugarscape.py:221-251` already switches on `agentDecisionModels` config to instantiate `Bentham`/`Asimov`/`Leader`/`Temperance` subclasses from `ethics.py` (each overrides `findBestEthicalCell`, e.g. `ethics.py:101-142`). v3 registers one more model, `"ruleset"`, backed by our subclass. Children spawned via the existing `spawnChild` override pattern (`ethics.py:98`, `:259`, …) carry the seat and ruleset.

## 6. Targets: literature-grounded outcome distributions

Every target is a **normalized histogram over a declared support**, plus a measurement recipe. One uniform representation covers two variable kinds:

- **Per-agent variables** (wealth, age, age-at-death, …): at each of the final `window` W ticks (default 100), sample the variable over the seat's living agents; pool all samples into the histogram. Pooling over a window smooths small-population noise.
- **Per-tick scalar variables** (population, mean trade price, sick fraction, …): one sample per tick over the window; histogram of the W samples. This captures both level and variability — an equilibrium target is a narrow histogram, an oscillation target is a wide or bimodal one.

Target spec: `{id, variable, scope: "seat"|"global", support:[lo,hi], bins:[edges], probs:[...], window, source}`. Values outside support clamp to edge bins.

**Catalog (v3.0), two families, each entry citing its source:**

*A. Canonical emergent results from the Sugarscape literature* — targets a Sugarscape scientist recognizes:

| id | variable | shape | source |
|---|---|---|---|
| `wealth.skewed-gini-0.5` | wealth (seat) | right-skewed, fat upper tail, Gini ≈ 0.5 | Epstein & Axtell 1996, ch. II (emergent inequality under G1+M; Animation II-4) |
| `wealth.egalitarian` | wealth (seat) | compressed, Gini ≤ 0.25 | counterfactual: "grow equality" — the interesting inverse problem |
| `population.carrying-capacity` | population (global) | narrow histogram at the G1+M carrying capacity | E&A ch. II |
| `age-at-death.survivorship` | age at death (seat) | life-table-like distribution under rule R | E&A ch. II–III |
| `tribe.convergence` | majority-tribe share (global) | mass near 1.0 (cultural convergence) | E&A ch. III (tag-flipping rule K) |
| `tribe.diversity` | majority-tribe share (global) | mass near 0.5 (stable split) | E&A ch. III |
| `disease.endemic` / `disease.eradicated` | sick fraction (global) | mass near a set prevalence / near 0 | E&A ch. V |
| `price.equilibrium` | mean trade price (global) | narrow histogram at p ≈ 1 | E&A ch. IV (bilateral trade converges toward equilibrium price with dispersion shrinking but persisting under finite vision) |

*B. Real-world empirical distributions* — per James's direction, targets should ultimately be **observed real-world distributions**, so the most explanatory ruleset is the one that grows reality: e.g. a national wealth distribution (US wealth Gini ≈ 0.85, lognormal body + Pareto tail), an observed life table for age-at-death, an epidemic prevalence curve. These enter the catalog as binned empirical histograms with citations to the underlying dataset. v3.0 ships a handful; the catalog is data (`targets/*.json`), so growing it is not a code change.

The DTL measurement machinery mostly exists already: per-tick `runtimeStats` includes Gini, wealth aggregates, trade price/volume, disease prevalence, tribe sizes (`sugarscape.py:82-95`, `:1365-1385`), and `graphStats` already bins age/sugar/spice and Lorenz points (`sugarscape.py:94`). v3 adds per-seat filtering.

**Scope semantics in multiplayer:** `seat`-scoped targets score each seat on its own subpopulation — players shape their own agents but interact through the shared world (resources, trade, combat, disease). `global`-scoped targets score every seat against the *same realized macro outcome*, but seats may hold *different* targets — a deliberate tug-of-war variant ("you want convergence, I want diversity"). Both are variant levers; the flagship ranked variant should start seat-scoped (cleaner attribution). Open question O3.

## 7. Scoring

**Metric: 1 − normalized Wasserstein-1 distance.** Both histograms live on the same declared support and bins; W1 is computed from the two CDFs (sum over bins of |CDF_measured − CDF_target| × bin width) and normalized by the support range, giving a distance in [0,1]. Score = `1 − W1_norm` ∈ [0,1], higher is better.

Why W1 and not KL (James's "KL div?" prompt) — considered and rejected:

- **KL is undefined/infinite on empty bins**, which are routine in a 250-sample histogram; players would face score cliffs unrelated to actual closeness, or we'd smooth with pseudo-counts and the metric becomes a tuning artifact.
- **KL ignores the metric structure of the support**: mass one bin away from target costs the same as mass at the far end. W1 is exactly "how far must mass move," so nearby shapes score nearby — a smooth gradient that rewards incremental ruleset improvement, which is what makes hill-climbing the game fun.
- **Bounded and comparable**: after normalization W1 lives in [0,1] regardless of variable units, so scores are comparable across targets and variants — important for the EWMA leaderboard.
- Jensen–Shannon divergence (symmetric, bounded, always finite) is the respectable middle ground; we compute and **report** it in results as a diagnostic, but rank on W1.

Edge cases: a seat with zero living agents through the whole measurement window scores 0 (with a results flag), so extinction is never a scoring dodge. Ties need no special encoding (scores are continuous; platform compares the scalar).

**Results schema (sketch):** `scores: [per-seat match score]` (the platform's ranking scalar, `docs/what-is-a-coworld.md` §1.4); per-seat details `{target_id, score, w1, js_divergence, submitted, ruleset_nodes, agents_final, histogram:[...]}`; episode-level scalars for qualification gates: `score.match_mean`, `score.match_min`, `result.population_final`, `result.gini_final`, `result.extinct` (gates evaluate `score.*`/`result.*` scalars — trap #3 in the platform doc).

## 8. Config surface

The game config = **curated DTL passthrough + coworld block**.

- **DTL passthrough**: the useful subset of `sugarscapeOptions` (`archived/v1/reference/dtl-python/config.json`) — world geometry and resource peaks/regrowth, seasons, pollution, agent endowment ranges (vision, movement, metabolism, max age), reproduction/replacement, combat (`environmentMaxCombatLoot`, aggression ranges), trade, lending, disease list and dynamics, tag/tribe settings. Excluded: GUI/debug/logging/profiling options (`headlessMode`, `interfaceWidth`, `screenshots`, `debugMode`, `logfile*`, …) — the coworld edge owns I/O.
- **Coworld block**: `players:[{name}]`, `tokens:[...]` (runner-injected), `seats`, `timesteps` (default 1000), `measurement_window` (default 100), per-seat `targets` assignment, `trait_ranges` (allowed [lo,hi] per trait), `ruleset_limits`, `player_connect_timeout_seconds`.
- **Scenario pools** — the mechanism for "most explanatory ruleset generator". A variant may declare `scenario_pool: [{config_overrides, targets}, ...]`; at boot the game picks one scenario deterministically from the episode seed. Players only learn the drawn scenario from their observation, so a competitive submitter must be a *generator*: observation → ruleset. A league running a pooled variant measures, via EWMA over episodes, exactly the cross-scenario explanatory power James wants. Fixed-scenario variants remain the simple case (and the certification fixture).

## 9. Leaderboard: EWMA over scores, single-player first-class

Verified during v2 design (v2-design.md §3, 2026-08-10) and still the plan: the platform ladder natively supports `ranking.algorithm = "score"` with `standing_aggregation = "ewma"` and `half_life_hours` (metta `app_backend v2/ladders/rankings/score.py`; config in `v2/ladders/config.py`). **No platform modification needed.** Because the score is an absolute distribution-match in [0,1] (not relative to opponents), single-player episodes are first-class: a 1-seat variant scores identically in kind to an 8-seat one, and the ladder needs no opponent pairing for rating to be meaningful. Elo is rejected: all-pairs win/loss comparison is meaningless for single-player episodes and lossy for absolute continuous scores. Within a league all episodes run one variant, so raw scores are EWMA-comparable; different targets/scenarios live in different leagues or inside one pooled variant (§8).

## 10. Architecture and repo layout

```
coworld_manifest.json          # template, {{GAME_IMAGE}} placeholders
compose.yaml                   # service names = role names, linux/amd64
Dockerfile                     # python:3.x-slim, pinned
config.json                    # local dev default
src/sugarscape/                # vendored DTL fork; UPSTREAM.md pins upstream commit
src/coworld/                   # the v3 edge (all new code):
    server.py                  #   WS edge: /healthz, /player, /global, /client/*
    ruleset.py                 #   DSL: parse, validate, compile-to-closures, interpret
    ruleset_agent.py           #   Agent subclass; registers as decision model "ruleset"
    seats.py                   #   seat assignment, inheritance on birth/replacement
    targets.py                 #   target catalog loading + measurement
    scoring.py                 #   histograms, W1, JS, results assembly
    replay.py                  #   frame log writer
targets/                       # catalog JSON, one file per target, with sources
players/baseline/              # bundled baseline player (Dockerfile + README)
replay-viewer/                 # static bundle source; output gitignored
tools/build_replay_viewer.sh
docs/PROTOCOL.md  docs/RULES.md  docs/TARGETS.md
tests/
```

- **DTL fork policy**: vendor the pinned upstream (same commit v1 pinned, or refreshed — open question O9), keep DTL files as untouched as possible; all v3 behavior lives in `src/coworld/` via the existing subclass/registration seams. The intended DTL-file diff is small: registering the decision model, seat tag on the agent, per-seat stats hook, and a headless entry point that skips GUI construction (`sugarscape.py:77` already guards on `headlessMode`).
- **The WS edge is thin and the sim is synchronous.** Python WS servers are async-flavored; the async stays confined to `server.py` (submission window + spectator fan-out), which hands a plain dict of rulesets to a fully synchronous `run_episode()`. During the run the sim thread emits frames into a queue the edge drains. (Library choice — `websockets` vs `aiohttp` vs threaded `simple-websocket` — is an implementation detail; candidate default: `websockets`.)
- **Baseline player**: reads the observation, picks from a small library of canned rulesets keyed on target variable/shape (e.g. greedy for skewed-wealth, pollution-averse spread-out rule for egalitarian), submits, exits. Deliberately beatable; gives the qualification gate and certification something real.
- **Certification fixture**: 20×20 world, ~30 agents, 2 seats, 50 ticks, fixed seed — runs in well under a second of sim time.

## 11. Replay and spectator

- **Replay artifact** (game-owned bytes): zlib-compressed JSON frame log — episode header (config, seed, per-seat targets + submitted rulesets + scores) then per-tick frames (agent id/seat/position/wealth, cell resource grid deltas, per-tick runtimeStats, and every K ticks each seat's running measured histogram). Config+seed+rulesets alone would suffice to *re-simulate*, but the browser can't run CPython, so v3.0 records presentation frames (v1's approach, with a leaner encoding).
- **Static replay-viewer bundle** (the platform's recommended path — `docs/what-is-a-coworld.md` §1.6): plain JS/canvas, no WASM needed since it only plays frames. Two panes: the map, and the star of the show — **each seat's measured histogram morphing over time against its target silhouette, with the running score**. The distribution-convergence view is the game's identity; the replay should make "did my rule grow the target?" visible at a glance. `?chrome=off` thumbnail mode supported.
- Live spectating (`/global`) streams the same frames.
- Future (explicit non-goal for v3.0): browser re-simulation via Pyodide, or porting the sim; not worth it while frame logs are ~single-digit MB.

## 12. Performance evidence (measured this session)

Benchmarked the pinned DTL Python headless on James's machine (Apple Silicon, CPython 3.14.4), default `config.json` (50×50 world, 250 starting agents, bentham decision model, reproduction on — population grows to ~1,050 by t=500 and stabilizes ~930 at t=999):

- 100 ticks: **1.37 s** wall.
- 1,000 ticks (full default episode): **52.5 s** wall — ≈ 19 ticks/s at ~1,000 agents, i.e. **~4% of the 20-minute hosted episode budget** (`episode_timeout_minutes` default 20).

Headroom conclusions: the ruleset interpreter can cost several × stock ranking cost before the budget matters (compiled closures over ≤ 24 candidate cells × ≤ 256 nodes); hosted CPUs are slower than an M-series laptop but the margin is ~19× even after reserving the full 180 s submission window; validation item V2 re-benchmarks with RulesetAgent in the loop before freezing ranked-variant sizes.

## 13. Risks

- **R1 — DSL expressivity vs. legibility.** Too weak → solved/boring; too strong → winning rulesets are opaque blobs and the "explanatory" framing dies. Mitigations: node budget, curated feature vocabulary, and the results echoing rulesets so the community can read winners. Tune after playtesting.
- **R2 — Degenerate strategies.** E.g. hitting an egalitarian target by keeping agents poor-but-alive, or extinction-adjacent play. The zero-agents rule and window pooling close the worst; expect a balancing pass on the catalog after real episodes.
- **R3 — Target achievability.** Some literature targets may be unreachable under some configs (or trivially reached by null ruleset). Each catalog entry needs a baseline calibration run recording the null-ruleset score, so variants can pick targets with real skill spread. (Validation V3.)
- **R4 — DTL code quality as a dependency.** DTL is a research codebase (1,662-line agent.py, global RNG, floats everywhere). We accept it as-is per the premise (clone, don't rewrite); the risk is contained by keeping our code at the subclass seam and pinning the fork.
- **R5 — CPython version pinning.** Determinism promise is per-pinned-interpreter; container pin makes hosted runs reproducible, local repro requires same version. Documented, not solved.

## 15. Alternatives considered (summary table for the doc)

| Decision | Chosen | Rejected | Why |
|---|---|---|---|
| Control model | one-shot ruleset submission | per-tick policy control (v1/v2) | premise of v3; kills the latency edge, makes DTL viable, makes episodes cheap |
| Sim implementation | direct DTL Python clone | from-scratch rewrite (v2's D1) | D1's rationale was the per-tick control seam; with it gone, cloning is fastest and truest to the literature |
| Ruleset form | declarative DSL (data) | code submission (Python/WASM) | sandboxing/determinism/legibility |
| DSL power | decision list + expr trees, budgeted | flat weight vector / Turing-complete | expressivity floor vs. halting+perf+audit ceiling |
| Scoring metric | 1 − normalized W1 (JS reported) | KL divergence | empty-bin infinities; no support metric; unbounded |
| Rating | platform-native score EWMA | Elo | single-player first-class; absolute continuous scores |
| Replay | frame log + static JS viewer | Pyodide/WASM resimulation | CPython in browser is heavy; frames are small at this scale |
| Async | thin async WS edge only, sync sim | async through the sim | James's no-async rule; sim has no I/O anyway |
