Design Proposal · 2026-08-11 · Rev 2 — comment round 1 applied

Sugarscape v3

One-shot ruleset submission over a direct DTL Sugarscape clone, scored by how closely the emergent outcome distribution matches a literature-grounded or real-world target. The player is a computational social scientist; the score is explanatory power.

Executive Summary

Sugarscape v3 replaces per-tick agent control — the defining (and persistently painful) feature of v1 and the never-implemented v2 — with a single up-front submission: each player hands the game a ruleset, a small declarative program of behavioral trait dials plus a movement decision list, and the simulation then free-runs to completion with zero player I/O. Because no per-tick control edge exists, the one argument for building our own simulator (v2's decision D1) dissolves, and v3 becomes a direct clone of the DTL Python Sugarscape (nkremerh/sugarscape, Unlicense) extended with one custom Agent subclass that interprets rulesets, plus a thin coworld WebSocket edge. Each seat is assigned a target outcome distribution — drawn from the Sugarscape literature or from real-world observed data — and scored by target-scaled Wasserstein-1 similarity between the measured and target histograms. Leaderboards rank players by an EWMA of these absolute scores, which the platform ladder already supports natively, so single-player episodes are first-class.

The most consequential choices a reviewer should weigh: the ruleset DSL (a budgeted decision list over JSON s-expressions — expressive enough to be a real game, total and deterministic by construction, legible enough that winning rulesets read as explanations); the scoring metric (W1 chosen over KL divergence, which is argued to be a trap in §7); and the fault model (a seat that never submits gets the null ruleset, which is by definition vanilla DTL behavior — no timeout machinery survives into the run). Measured performance gives ample headroom: a full 1,000-tick default episode runs in 52.5 s on an M-series laptop, about 4% of the 20-minute hosted episode budget. Ten open questions were flagged for James; comment round 1 (2026-08-11) resolved seven of them — including the DSL's name, SugarLang, and the flip to global-scope targets by default (§15).

1 · Where This Comes From

  • v1 (frozen) bolted per-tick movement control onto a Nim port of DTL; it worked but the synchronous decision edge was slow — worst case ~6.4 s per timestep with 64 seats timing out.
  • v2 (design-complete, never implemented) justified a from-scratch rewrite with exactly one argument: DTL has no seam for external per-tick controllers.
  • v3 removes per-tick control entirely, which dissolves that argument — cloning DTL becomes the cheapest correct choice.

This is the third generation of the Sugarscape coworld, and each generation is defined by its answer to one question: how do players touch the simulation?

v1 (archived/v1/, frozen) was a byte-parity Nim port of the DTL Python Sugarscape with per-tick, per-agent movement control bolted on over WebSocket. It worked and was certified, but the decision edge was synchronous and slow — worst case ~6.4 s per timestep with 64 seats timing out — and only movement could be delegated.

v2 (archived/v2/, design-complete, never implemented) was a from-scratch deterministic Nim implementation with agent-level player control, a phased timestep, and negotiation. Its decision D1 ("v2 is our own implementation of Sugarscape, not DTL" — docs/what-is-a-coworld.md §Decisions) rested on exactly one thing: DTL is a batch social-science simulator with no seam for external per-tick controllers, so per-tick control could only ever be bolted on.

v3 is James's direction of 2026-08-11: players do not control agents per tick. Each player submits, once, a ruleset — a declarative specification of the movement rule their agents will follow — and the simulation runs to completion with no further player interaction. This dissolves D1's rationale entirely. With no per-tick control edge, DTL's batch architecture stops being an obstacle and becomes the cheapest correct choice.

Decision — clone DTL, don't rewrite

v3 is a direct clone of the DTL Python implementation (nkremerh/sugarscape, Unlicense, pinned copy at archived/v1/reference/dtl-python/), extended with one custom Agent subclass that interprets rulesets, plus a thin coworld edge. D1's sole justification was the per-tick control seam; with that gone, cloning is fastest and truest to the literature the game is built on.

James's framing of the goal: across episodes, the winning player is the one with the most explanatory ruleset (or ruleset generator) — one that, applied to many different Sugarscape configurations and many different target distributions (drawn from the Sugarscape literature and from real-world observed distributions), reliably makes the simulation's emergent outcome match the target.

Framing This is Epstein's generative social science motto operationalized as a game: "If you didn't grow it, you didn't explain it." The player is cast as a computational social scientist; the score is explanatory power.

2 · Game Concept

  • Each seat gets a target outcome distribution — delivered as binned data, never prose — plus the full game config; it answers with one ruleset.
  • The DTL simulation runs N ticks (default 1,000) with no further interaction, then measures each seat's actual outcome distribution.
  • Score = closeness of measured to target; leaderboards use an EWMA of episode scores, not Elo, so single-player episodes are first-class.

An episode assigns each player (seat) a target outcome distribution — for example "a wealth distribution with a Pareto tail and Gini ≈ 0.5" or "endemic disease at 20% prevalence" — plus the full game config. The target is delivered as pure data: the observation carries the declared support, bin edges, and target probabilities (plus the measurement window and a citation string for humans) — never a natural-language description a policy would have to parse. Each player answers with a single ruleset: a small declarative program (traits plus a movement decision list) that all agents assigned to that seat will follow. The DTL simulation then runs N ticks (default 1,000). At the end, the game measures the actual outcome distribution for each seat and scores it by distance to that seat's target — closer is better. Leaderboards rank players by an EWMA of episode scores rather than Elo, so single-player episodes are first-class rather than a degenerate case.

3 · Episode Flow & Player Protocol

  • Four phases: boot → submission window → free run → score & write. All player I/O happens in the submission window.
  • The window closes when every seat has a valid ruleset, or after player_connect_timeout_seconds (default 180 s).
  • Fault semantics are trivial by construction: a non-submitting seat gets the null ruleset, which is exactly vanilla DTL behavior, and is still scored honestly.
  • Every phase and sub-phase is timed precisely; the timings ship as structured logs plus a timings block in the results.

An episode proceeds through four phases:

  1. Boot. The game container reads config from COGAME_CONFIG_URI, seeds the RNG, builds the DTL world, and serves /healthz.
  2. Submission window. Each player connects to WS /player?slot=n&token=t (a bad token is rejected at the handshake, per the platform contract). The game immediately sends one observation. The player replies with one action — the ruleset — and may disconnect. The window closes when all seats have submitted valid rulesets, or after player_connect_timeout_seconds (default 180 s).
  3. Run. The simulation free-runs N ticks with zero player I/O. Spectator frames stream to WS /global as it runs.
  4. Score & write. The game measures distributions over the final window, computes scores, writes the results JSON to COGAME_RESULTS_URI and the replay artifact to COGAME_SAVE_REPLAY_URI, sends a final result message to any still-connected clients, and exits.

Instrumentation (added in comment round 1). The game image records precise wall-clock timings for every phase and sub-phase: world construction, per-seat connect time, observation and action transit times, validation cost, per-tick simulation cost with a sub-step breakdown (movement/ruleset evaluation, trade, reproduction, lending, disease, stats collection), measurement, scoring, and each artifact write. Timings are emitted as structured log lines and aggregated into a timings block in the results JSON, so every hosted episode doubles as a profile. This is the substrate for knowing what — if anything — is worth optimizing (§12).

Messages

Messages are game-owned JSON over WebSocket — the platform fixes only routes and tokens (docs/what-is-a-coworld.md §1.2):

DirectionMessagePayload
Game → playerobservation {type, protocol:"sugarscape-v3/1", seat:n, config:{…full effective game config…}, target:{id, variable, scope, support:[lo,hi], bins:[…], probs:[…], window, source}, ruleset_schema:{version:1, limits:{max_nodes:256, max_depth:16, max_bytes:32768}}}
Player → gameaction {type:"action", ruleset:{…}}
Game → playerack {type:"ack", valid:true} or {type:"ack", valid:false, errors:[…]} — an invalid ruleset can be corrected and resubmitted until the window closes

Decision — fault semantics: null ruleset = vanilla DTL

Fault handling is trivial by construction. After the submission window there is nothing left for a player to fault on — contrast v1's 100 ms fallback machinery and v2's frozen-agent rule A3. A seat that never submits a valid ruleset gets the null ruleset — no trait overrides, no movement rules — which by definition (§4 semantics) is exactly vanilla DTL behavior. The seat is still scored honestly against its target, and the results record submitted:false for it. No timeout, reconnect, or degraded-mode logic survives into the run phase at all.

4 · The Ruleset DSL — SugarLang

  • Two optional blocks: traits (scalar dials onto per-agent factors DTL already implements) and movement (an ordered decision list of budgeted score expressions).
  • Total and deterministic by construction — it is data, not code; nothing to sandbox, nothing that can fail to halt.
  • Budgets: ≤ 256 nodes, depth ≤ 16, ≤ 32 KB JSON, validated at submission; expressions compile once to closures.
  • Both blocks absent = the null ruleset = a vanilla DTL agent.

The DSL — named SugarLang (decided in comment round 1) — is the heart of the design. The requirements pull in four directions at once: it must be expressive enough that ruleset design is a real intellectual game; total and deterministic (no halting problem, no sandbox escape — it is data, not code); cheap to evaluate inside the per-tick movement loop; and legible enough that a leaderboard-topping ruleset can be read and understood — that legibility is the scientific payoff.

Shape

{
  "version": 1,
  "traits": { "aggression": 0.0, "trade": 1.0, "lending": 0.0, "fertility": 1.0 },
  "movement": [
    { "if":    ["<", ["get","agent.ttl"], 3],
      "score": ["get","cell.welfare"] },
    { "score": ["-", ["get","cell.welfare"],
                ["*", 0.4, ["get","cell.distance"]],
                ["*", 2.0, ["get","cell.pollution"]]] }
  ]
}

Two blocks, both optional — and both absent is the null ruleset, i.e. a vanilla DTL agent:

traits are scalar behavioral dials applied to every agent of the seat at spawn, clamped into per-variant allowed ranges. The v3.0 traits map directly onto per-agent factors DTL already implements: aggression → aggressionFactor (combat, agent.py:717); trade → tradeFactor (agent.py:601-603 — 0 disables trading); lending → lendingFactor (agent.py:432); fertility → fertilityFactor (agent.py:501). This buys player control over combat, trade, lending, and reproduction intensity without touching those subsystems' code — DTL already parameterizes them per agent. A variant locks a dial by declaring a degenerate range.

movement is an ordered decision list. Each tick, when the agent moves, the if conditions (expressions over agent/world state) are evaluated top-down; the first matching rule supplies the score expression (a rule with no if always matches, and the list must end with one). The score expression is evaluated once per candidate cell, and the agent moves to the argmax cell. Ties break by smaller travel distance, then DTL's existing shuffled iteration order — the identical tie policy to stock DTL (agent.py:1430-1434), preserving determinism.

Expressions

Expressions are JSON s-expressions: ["op", arg, arg, …], numbers as literals, ["get", "name"] for features. The operator set: + - * / min max abs neg pow < <= > >= == != and or not if. Totality rules make every expression a total function: division by zero yields 0; pow with base < 0 or |exponent| > 8 is clamped; all results are finite floats (NaN/Inf → 0). Budgets, validated at submission time: at most 256 nodes total per ruleset, depth at most 16, at most 32 KB of JSON. Evaluation is O(nodes) per candidate cell; the interpreter compiles each expression once to nested Python closures at submission time, so per-eval cost is small.

Feature vocabulary (v3.0)

NamespaceFeaturesSource in DTL
agent.* sugar, spice, wealth, sugarMetabolism, spiceMetabolism, vision, movement, age, ttl, mrs direct attributes; ttl = findTimeToLive() (agent.py:1114), mrs = findMarginalRateOfSubstitution() (agent.py:1024)
cell.* sugar, spice, pollution, distance, occupied, preyWealth, welfare candidate record from rankCellsInRange() (agent.py:1396-1444); welfare = DTL's own Cobb–Douglas findWelfare() for this agent at this cell (agent.py:1171-1202), so the stock greedy rule is expressible as ["get","cell.welfare"]
world.* timestep, population, gini, meanWealth per-tick runtimeStats DTL already computes (sugarscape.py:82-95)
Why world.* matters The world.* namespace is a deliberate differentiator: it lets rulesets be macro-feedback controllers ("if Gini is above target, favor poor-agent-friendly moves"), which is precisely the skill the game wants to reward — steering emergent distributions.

Semantics guarantees

  • The candidate cell set is unchanged from DTL — vision, occupancy, prey-validity and retaliation filtering all still apply (agent.py:1413-1428). The ruleset only replaces the ranking among valid candidates. Combat stays a movement consequence exactly as in DTL: moving onto a valid prey cell is an attack, so rules can seek or avoid combat via cell.occupied/cell.preyWealth.
  • Everything downstream of movement — collection, metabolism, trade, reproduction, lending, disease, aging, death, inheritance (agent.py:569-599 doTimestep) — runs stock DTL code, modulated only through the trait dials.
  • Deterministic: one seeded random.Random stream (DTL uses the global random module, seeded once), a pure interpreter, and a fixed tie policy. Same config + seed + rulesets ⇒ an identical run on the same CPython version. The container pins the Python version, so hosted runs are reproducible; we do not promise cross-version bit-stability.

Alternatives rejected for the DSL

  • Arbitrary code submission (Python snippet / WASM blob). Maximum expressivity, but the sandboxing, resource-abuse, and determinism burdens are all severe, and winning rulesets would be unreadable. The DSL is data; there is nothing to escape.
  • Flat weight vector over fixed features (score = w·f). Trivially safe but no conditionality; the game collapses into linear regression and the expressivity ceiling is hit in a week.
  • Turing-complete rule language (loops/recursion, full GP). Halting and performance problems inside a 1,000-tick × ~1,000-agent × ~24-candidate loop; audit burden; overkill for movement.

A side benefit of the chosen design: s-expression trees are the standard representation that genetic programming evolves (Koza 1992), so SugarLang is naturally friendly to players who want to evolve rulesets offline. (An earlier draft called this "the classic GP-on-Sugarscape formulation" — softened on review: GP has been applied to Sugarscape-style agent rules, but no specific canonical paper is being claimed.)

5 · Seats, Agents & Lifecycle

  • Initial agents are dealt round-robin; validation requires startingAgents % seats == 0, so allocation at t=0 is equal.
  • Replacements inherit the replaced agent's seat; newborns take a parent's seat by seeded 50/50 draw.
  • RulesetAgent plugs into DTL's existing decision-model registration seam — the same one the ethics subclasses already use.

Config declares seats (the number of player slots) alongside DTL's startingAgents. Validation requires startingAgents % seats == 0, and initial agents are assigned round-robin, so the allocation at t=0 is equal across seats.

Two lifecycle events can add agents mid-run, and each has a seat rule. Replacements (DTL's agentReplacements rule R): a replacement agent inherits the seat of the agent it replaces. Newborns (DTL reproduction): the child is assigned to one of its two parents' seats by a 50/50 draw from the simulation's seeded RNG stream. v2's fancier Thue–Morse alternation is noted as an option if the 50/50 draw proves noisy, but it is not in v3.0 (open question O8).

RulesetAgent instantiation follows DTL's existing decision-model seam: sugarscape.py:221-251 already switches on the agentDecisionModels config to instantiate Bentham/Asimov/Leader/Temperance subclasses from ethics.py, each of which overrides findBestEthicalCell (e.g. ethics.py:101-142). v3 registers one more model, "ruleset", backed by our subclass. Children are spawned via the existing spawnChild override pattern (ethics.py:98, ethics.py:259, …) and carry the seat and ruleset with them.

6 · Targets: Literature-Grounded Outcome Distributions

  • Every target is a normalized histogram over a declared support, plus a measurement recipe; one representation covers per-agent and per-tick variables.
  • The catalog has two families: canonical emergent results from the Sugarscape literature, and real-world empirical distributions.
  • The catalog is data (targets/*.json) — growing it is not a code change.
  • Global scope is the default (comment round 1): every seat is scored on the same shared outcome, so rulesets compete to steer it. Seat scope ships at launch as a variant option.

Every target is a normalized histogram over a declared support, plus a measurement recipe. One uniform representation covers two kinds of variable:

  • Per-agent variables (wealth, age, age-at-death, …): at each of the final window W ticks (default 100), the variable is sampled over the scope's living agents — all living agents under the default global scope, the seat's own under seat scope — and all samples are pooled into the histogram. Pooling over a window smooths small-population noise.
  • Per-tick scalar variables (population, mean trade price, sick fraction, …): one sample per tick over the window; the histogram is of the W samples. This captures both level and variability — an equilibrium target is a narrow histogram, an oscillation target is a wide or bimodal one.

The target spec is {id, variable, scope: "global" (default) | "seat", support:[lo,hi], bins:[edges], probs:[…], window, source}. Values outside the support clamp to the edge bins. This spec — bin edges and probabilities as plain data — is exactly what the observation message delivers to the player (§3); the source citation string is for humans, and no policy ever parses natural language.

Catalog (v3.0)

Family A — canonical emergent results from the Sugarscape literature, targets a Sugarscape scientist recognizes on sight:

Every catalog entry defaults to global scope — including the per-agent variables like wealth and age-at-death, which are then measured over the whole population. A variant may override any entry to seat scope.

Family B — real-world empirical distributions. Per James's direction, targets should ultimately be observed real-world distributions, so that the most explanatory ruleset is the one that grows reality: for example a national wealth distribution (US wealth Gini ≈ 0.85, lognormal body plus Pareto tail), an observed life table for age-at-death, or an epidemic prevalence curve. These enter the catalog as binned empirical histograms with citations to the underlying dataset. v3.0 ships a handful; the catalog is data (targets/*.json), so growing it is not a code change.

Status of the data (comment round 1) Neither family's histograms have been gathered yet — the tables above name the shapes and their sources, not finished data files. Assembling, binning, and citing the actual target histograms (digitizing the E&A results for Family A; sourcing real datasets for Family B) is an explicit implementation task, and Family A entries additionally need the R3 calibration runs before a variant ships them.

The DTL measurement machinery mostly exists already: per-tick runtimeStats includes Gini, wealth aggregates, trade price/volume, disease prevalence, and tribe sizes (sugarscape.py:82-95, sugarscape.py:1365-1385), and graphStats already bins age/sugar/spice and Lorenz points (sugarscape.py:94). v3 adds per-seat filtering on top.

Decision — global scope is the default (comment round 1)

global-scoped targets score every seat against the same realized macro outcome, while seats may hold different targets. That makes multiplayer a contest of rulesets competing to steer one shared system: other players' targets will sometimes be amenable to yours, sometimes orthogonal — and occasionally directly incompatible. Direct incompatibility is a benefit, not something to avoid; it is where the steering skill shows. seat-scoped targets (each seat scored on its own subpopulation, interacting through the shared world) remain a supported variant option at launch for leagues that want cleaner attribution. This flips the first draft's recommendation, which had the flagship starting seat-scoped.

7 · Scoring

Amended 2026-08-18 Support-width normalization was replaced by target-scaled hyperbolic W1 after probe calibration exposed misleadingly high scores for collapsed distributions. The decision, migration, and evidence are recorded in the scoring-v2 design.
  • Score = S / (S + D), where D is raw Wasserstein-1 distance and S is the target's characteristic binned spread, in [0,1], higher is better.
  • KL divergence — James's initial prompt — was considered and rejected: empty-bin infinities, no metric structure, and it breaks cross-target comparability.
  • Jensen–Shannon divergence is computed and reported as a diagnostic, but ranking is on W1.
  • An empty measurement scores 0 — population extinction under global scope, own-agents extinction under seat scope. Extinction is never a scoring dodge.

Both histograms live on the same declared support and bins. W1 is computed from the two CDFs — the sum over bins of |CDFmeasured − CDFtarget| × bin width — and compared with a target-derived scale S: the greater of its binned mean absolute deviation from the leftmost median and that median bin's width. The score is S / (S + D) ∈ (0,1], higher is better. Intuitively, W1 is the work required to move probability mass from where the simulation put it to where the target wants it; the score rewards getting the mass close even when the shape is not yet exact.

Decision — W1, not KL divergence

KL divergence (James's "KL div?" prompt) was considered and rejected for three concrete reasons:

  • KL is undefined or infinite on empty bins, which are routine in a 250-sample histogram. Players would face score cliffs unrelated to actual closeness — or we would smooth with pseudo-counts and the metric would become a tuning artifact.
  • KL ignores the metric structure of the support: mass one bin away from the target costs the same as mass at the far end. W1 is exactly "how far must mass move," so nearby shapes score nearby — a smooth gradient that rewards incremental ruleset improvement, which is what makes hill-climbing the game fun.
  • Bounded and interpretable: target scaling removes variable units; 0.5 means one characteristic target scale of transport, so support bounds no longer dictate apparent quality.

Jensen–Shannon divergence (symmetric, bounded, always finite) is the respectable middle ground; v3 computes and reports it in the results as a diagnostic, but ranks on W1.

Edge cases

An empty measurement scores 0, with a flag in the results — under the default global scope that means the whole population went extinct before or during the window (every seat scores 0); under seat scope it means that seat's own agents did. Either way, extinction is never a scoring dodge. Ties need no special encoding: scores are continuous and the platform compares the scalar.

Qualification gates evaluate score.*/result.* scalars — trap #3 in the platform doc.

8 · Config Surface

  • Game config = curated DTL passthrough + a coworld block; GUI/debug/logging options are excluded because the coworld edge owns I/O.
  • Scenario pools are the mechanism that makes "most explanatory ruleset generator" measurable — and they ship in v3.0 (comment round 1).

DTL passthrough. The useful subset of sugarscapeOptions (archived/v1/reference/dtl-python/config.json): world geometry and resource peaks/regrowth, seasons, pollution, agent endowment ranges (vision, movement, metabolism, max age), reproduction/replacement, combat (environmentMaxCombatLoot, aggression ranges), trade, lending, the disease list and dynamics, and tag/tribe settings. Excluded: GUI, debug, logging, and profiling options (headlessMode, interfaceWidth, screenshots, debugMode, logfile*, …) — the coworld edge owns I/O.

Concretely, the world-shape keys look like this (values from the DTL default config — the classic two-resource map: sugar mountains in the NE/SW corners, spice in NW/SE):

"environmentWidth": 50, "environmentHeight": 50, "environmentWraparound": true,
"environmentSugarPeaks": [[15, 35, 4], [35, 15, 4]],   // [x, y, peak height]
"environmentSpicePeaks": [[15, 15, 4], [35, 35, 4]],   // resources decay radially
"environmentMaxSugar": 4, "environmentSugarRegrowRate": 1,      // per-cell cap, α
"environmentSeasonInterval": 0,          // >0 enables N/S seasonal growback (S rule)
"environmentPollutionTimeframe": [0, 0], // enables production/consumption pollution
"agentVision": [1, 6], "agentMovement": [1, 6],        // per-agent endowment ranges
"agentSugarMetabolism": [1, 4], "agentSpiceMetabolism": [1, 4],
"agentMaxAge": [60, 100], "agentFertilityFactor": [1, 1], ...

Endowment ranges are [min, max] pairs rolled per agent at spawn; peak lists are arbitrary — a variant can build one-peak, three-peak, or asymmetric maps by editing data alone.

Coworld block. players:[{name}], tokens:[…] (runner-injected), seats, timesteps (default 1,000), measurement_window (default 100), the per-seat targets assignment, trait_ranges (allowed [lo,hi] per trait), ruleset_limits, and player_connect_timeout_seconds.

Scenario pools — the mechanism for "most explanatory ruleset generator." A variant may declare scenario_pool: [{config_overrides, targets}, …]; at boot the game picks one scenario deterministically from the episode seed. Players only learn the drawn scenario from their observation, so a competitive submitter must be a generator: observation → ruleset. A league running a pooled variant measures, via EWMA over episodes, exactly the cross-scenario explanatory power James wants. Fixed-scenario variants remain the simple case — and the certification fixture. Scenario pools ship in v3.0 (decided — O4, comment round 1), not deferred to a later release.

9 · Leaderboard: EWMA Over Scores

  • The platform ladder natively supports score-based EWMA ranking — no platform modification needed.
  • Because the score is an absolute distribution match in [0,1], single-player episodes are first-class; Elo is rejected.

Verified during the v2 design (archived/v2/v2-design.md §3, 2026-08-10) and still the plan: the platform ladder natively supports ranking.algorithm = "score" with standing_aggregation = "ewma" and half_life_hours (metta app_backend v2/ladders/rankings/score.py; config in v2/ladders/config.py). No platform modification is needed.

Because the score is an absolute distribution match in [0,1] — not relative to opponents — single-player episodes are first-class: a 1-seat variant scores identically in kind to an 8-seat one, and the ladder needs no opponent pairing for the rating to be meaningful. Elo is rejected: all-pairs win/loss comparison is meaningless for single-player episodes and lossy for absolute continuous scores. Within a league all episodes run one variant, so raw scores are EWMA-comparable; different targets and scenarios live in different leagues, or inside one pooled variant (§8).

10 · Architecture & Repo Layout

  • Vendored DTL fork kept as untouched as possible; all v3 behavior lives in src/coworld/ via existing subclass/registration seams.
  • The WS edge is thin and async-confined; the simulation itself is fully synchronous.
  • A deliberately beatable baseline player and a sub-second certification fixture ship in-repo.

DTL fork policy. Vendor a fresh pin of current upstream nkremerh/sugarscape HEAD at implementation time (decided — O9, comment round 1; not v1's older copy), record the commit in UPSTREAM.md, and keep the DTL files as untouched as possible; all v3 behavior lives in src/coworld/ via the existing subclass and registration seams. The intended DTL-file diff is small: registering the decision model, a seat tag on the agent, a per-seat stats hook, and a headless entry point that skips GUI construction (sugarscape.py:77 already guards on headlessMode).

The WS edge is thin and the sim is synchronous. Python WS servers are async-flavored; the async stays confined to server.py (the submission window plus spectator fan-out), which hands a plain dict of rulesets to a fully synchronous run_episode(). During the run the sim thread emits frames into a queue the edge drains. The library choice — websockets vs aiohttp vs threaded simple-websocket — is an implementation detail; the candidate default is websockets.

Baseline player. Reads the observation, picks from a small library of canned rulesets keyed on target variable and shape (greedy for skewed-wealth, a pollution-averse spread-out rule for egalitarian, …), submits, and exits. It is deliberately beatable; it gives the qualification gate and certification something real to test against.

Certification fixture. A 20×20 world, ~30 agents, 2 seats, 50 ticks, fixed seed — it runs in well under a second of sim time.

11 · Replay & Spectator

  • Replay artifact: zlib-compressed JSON frame log — header (config, seed, targets, rulesets, scores) plus per-tick frames.
  • The static JS/canvas viewer's star pane is each seat's measured histogram morphing toward its target silhouette with a running score.
  • Frame log vs. WASM re-simulation is gated on the measured zlib size of real episode logs; James reviews the implemented viewer before it ships.

Replay artifact (game-owned bytes): a zlib-compressed JSON frame log — an episode header (config, seed, per-seat targets plus submitted rulesets plus scores) followed by per-tick frames (agent id/seat/position/wealth, cell resource grid deltas, per-tick runtimeStats, and every K ticks each seat's running measured histogram). Config + seed + rulesets alone would suffice to re-simulate, but the browser can't run CPython, so v3.0 records presentation frames — v1's approach, with a leaner encoding.

Static replay-viewer bundle — the platform's recommended path (docs/what-is-a-coworld.md §1.6): plain JS/canvas, no WASM needed since it only plays frames. Two panes: the map, and the star of the show — each seat's measured histogram morphing over time against its target silhouette, with the running score. The distribution-convergence view is the game's identity; the replay should make "did my rule grow the target?" visible at a glance. A ?chrome=off thumbnail mode is supported. Review checkpoint (comment round 1): James reviews the implemented viewer and iterates on it before it ships — the pane layout above is a starting point, not a settled spec.

Live spectating (/global) streams the same frames.

Decision gate — frame log vs. WASM resimulation (comment round 1) Measure the zlib-compressed frame-log size on real episodes first. If it lands in the expected single-digit-MB range, the frame log stays and browser re-simulation remains future work. If it comes out too heavy, revisit compiling the sim to WASM (Pyodide/py2wasm) so the replay artifact shrinks to config + seed + rulesets. The known cost of that path: CPython-in-WASM typically runs several times slower than native, so a 52.5 s episode could take minutes to resimulate in-browser — viable only with progressive playback (simulate ahead of the playhead), which is real viewer complexity. The artifact format is game-owned bytes either way, so the choice can change without a platform contract change.

12 · Performance Evidence

  • Measured this session: a full 1,000-tick default episode takes 52.5 s wall — about 4% of the 20-minute hosted episode budget.
  • Budget headroom is not a license: the SugarLang interpreter targets ≤ 2× stock ranking cost, verified by the §3 instrumentation.
  • Validation item V2: re-benchmark with RulesetAgent in the loop before freezing ranked-variant sizes.

The pinned DTL Python was benchmarked headless on James's machine (Apple Silicon, CPython 3.14.4) with the default config.json: a 50×50 world, 250 starting agents, the bentham decision model, reproduction on — population grows to ~1,050 by t=500 and stabilizes around ~930 at t=999.

Headroom conclusions: the ruleset interpreter can cost several times the stock ranking cost before the budget matters (compiled closures over ≤ 24 candidate cells × ≤ 256 nodes). Hosted CPUs are slower than an M-series laptop, but the margin is ~19× even after reserving the full 180 s submission window ((1,200 s − 180 s) / 52.5 s). Headroom is not a license (comment round 1): the interpreter should still be as efficient as reasonably possible — expressions compile once to nested closures (no tree-walking per evaluation), per-agent features are computed once per tick and shared across candidate cells, world features once per tick and shared across agents, and the hot path allocates nothing per evaluation. Working target: ≤ 2× stock ranking cost, measured by the §3 sub-step instrumentation.

Future work — speeding up the sim itself. The DTL implementation is unoptimized research code; profiling-guided improvement (hot-loop micro-optimization, caching neighborhood computations, or simply running the container under PyPy, which is often several-fold faster on pure-Python workloads) is a real option once the §3 instrumentation shows where the time goes. Not v3.0 scope; the instrumentation exists precisely so this can be decided from data.

13 · Risks

  • The two design-level risks are DSL expressivity-vs-legibility (R1) and degenerate strategies against targets (R2).
  • The two dependency-level risks are DTL code quality (R4) and CPython version pinning (R5); target achievability (R3) is closed by calibration runs.
R1 — DSL expressivity vs. legibility Too weak → solved and boring; too strong → winning rulesets are opaque blobs and the "explanatory" framing dies. Mitigations: the node budget, the curated feature vocabulary, and results echoing rulesets so the community can read winners. Tune after playtesting.
R2 — Degenerate strategies E.g. hitting an egalitarian target by keeping agents poor-but-alive, or extinction-adjacent play. The zero-agents rule and window pooling close the worst cases; expect a balancing pass on the catalog after real episodes.
R3 — Target achievability Some literature targets may be unreachable under some configs — or trivially reached by the null ruleset. Each catalog entry needs a baseline calibration run recording the null-ruleset score, so variants can pick targets with real skill spread. (Validation V3.)
R4 — DTL code quality as a dependency DTL is a research codebase (a 1,662-line agent.py, global RNG, floats everywhere). We accept it as-is per the premise — clone, don't rewrite. The risk is contained by keeping our code at the subclass seam and pinning the fork.
R5 — CPython version pinning The determinism promise is per-pinned-interpreter; the container pin makes hosted runs reproducible, but local reproduction requires the same version. Documented, not solved.
